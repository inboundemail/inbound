Inbound presents received email through a managed IMAP mailbox rather than a conventional standalone mail store. `INBOX`, `Junk` and scope folders are views of the mail Inbound has received, so some operations behave differently than on a traditional IMAP server.

## Default folders

Each mailbox credential includes these folders:

| Folder | Special-use attribute | Behavior |
| --- | --- | --- |
| `INBOX` | None | Incoming mail from every configured scope, except junk |
| `Sent` | `\Sent` | Automatically saved mailbox sends and client-saved sent messages, deduplicated by Message-ID |
| `Drafts` | `\Drafts` | For client-saved drafts |
| `Trash` | `\Trash` | For client-organized messages |
| `Junk` | `\Junk` | Incoming mail marked as junk, from every configured scope. See [Junk](#junk) |
| `Archive` | `\Archive` | Archived messages, shared with the mailbox HTTP API |

The personal namespace is `""` and the hierarchy separator is `/`. `INBOX` and the special-use folders cannot be deleted or renamed. With a `read_write` credential you can create, rename, and delete other folders. Renaming a folder also renames its subfolders. Creating or renaming onto an existing name returns `NO [ALREADYEXISTS]`.

Folders, flags, and appended messages belong to one credential. Other credentials on the same account don't see them.

### Scope folders

Every configured scope also appears as a folder under `Scopes`:

```text
INBOX
Sent
Drafts
Trash
Junk
Archive
Scopes/*@example.com
Scopes/support@another-example.com
```

`Scopes` is a non-selectable container (`\Noselect`), and its name is reserved. A domain scope appears as `Scopes/*@example.com`; an address scope appears as `Scopes/support@example.com`.

Scope folders are filtered views of the same messages as `INBOX` (junk mail appears only in `Junk`). They always open read-only, even for `read_write` credentials. You cannot append, move, or copy messages into a scope folder, change flags in it, or expunge from it. A `read_write` credential can copy messages from a scope folder into a writable folder.

## Capabilities

The server advertises exactly these capabilities:

```text
IMAP4rev1 APPENDLIMIT=1048576 AUTH=PLAIN CHILDREN ENABLE ID IDLE MOVE NAMESPACE SASL-IR SPECIAL-USE UIDPLUS UNSELECT UTF8=ACCEPT WITHIN
```

Supported commands:

- Authentication: `LOGIN` and `AUTHENTICATE PLAIN` (with `SASL-IR`). A `PLAIN` authorization identity different from the login email is rejected.
- Folders: `LIST`, `LSUB`, `NAMESPACE`, `SELECT`, `EXAMINE`, `STATUS`, `CREATE`, `RENAME`, `DELETE`, `SUBSCRIBE`, `UNSUBSCRIBE`.
- Messages: `FETCH`, `SEARCH`, `STORE`, `COPY`, `MOVE`, and their `UID` forms, plus `EXPUNGE`, `UID EXPUNGE`, `APPEND`, `CLOSE`, `UNSELECT`, `CHECK`, `NOOP`, and `IDLE`.
- `ENABLE UTF8=ACCEPT`. Other `ENABLE` arguments are ignored.

`COPY` and `APPEND` return `COPYUID` and `APPENDUID`. `MOVE` returns `COPYUID` followed by an untagged `EXPUNGE` for every moved message, and moving a message into the folder it's already in returns `NO`. `EXPUNGE` and `UID EXPUNGE` send an untagged `EXPUNGE` for each removed message.

`SUBSCRIBE` and `UNSUBSCRIBE` persist per credential; `LSUB` returns subscribed folders.

Extensions that aren't advertised are not supported, including `STARTTLS` (use implicit TLS on port `993`), `CONDSTORE`, `QRESYNC`, `QUOTA`, `COMPRESS=DEFLATE`, `SORT`, `THREAD`, `ACL`, OAuth (`XOAUTH2` or `OAUTHBEARER`), and the Gmail-only `XLIST`. Requests that would enable `CONDSTORE`, such as `SELECT (CONDSTORE)` or `SEARCH MODSEQ`, are rejected.

### Search

`SEARCH` supports sequence sets, `UID`, flag and keyword keys (such as `SEEN`, `UNSEEN`, `DELETED`, `FLAGGED`, `KEYWORD`), `BEFORE`/`ON`/`SINCE`, `SENTBEFORE`/`SENTON`/`SENTSINCE`, `LARGER`/`SMALLER`, `OLDER`/`YOUNGER` (`WITHIN`), `HEADER`, `FROM`, `TO`, `CC`, `BCC`, `SUBJECT`, `BODY`, `TEXT`, `OR`, and `NOT`.

- Text searches are case-insensitive substring matches. For received mail they match Inbound's parsed fields: `SUBJECT`, the address headers, and the plain-text body. `TEXT` checks the subject and plain-text body, so text that exists only in an HTML part may not match. For appended messages they match the raw message.
- `HEADER` searches on other header names match the raw message.
- `SENTBEFORE`, `SENTON`, and `SENTSINCE` use the parsed `Date` header of received mail and don't match appended messages. `BEFORE`, `ON`, `SINCE`, `OLDER`, and `YOUNGER` use the internal date, which is when Inbound received the message.
- `\Recent` is never set, so `RECENT` and `NEW` match nothing.
- Search keys the server doesn't implement are ignored instead of rejected, which can return more messages than requested. Filter results in your application when exact matching matters.

## New-message notifications

During `IDLE`, the server sends `EXISTS` as soon as new mail is synchronized into the selected folder, including mail addressed to a secondary envelope recipient. Outside `IDLE`, new messages are reported on the next command, such as `NOOP`. Active sessions are also refreshed about every 60 seconds as a fallback.

An `IDLE` command ends after 30 minutes: the server sends `* BYE IDLE terminated` and closes the connection. Reissue `IDLE` before then (most clients restart it every 29 minutes) or reconnect automatically.

## Flags and read state

Writable credentials can set standard flags (`\Seen`, `\Answered`, `\Flagged`, `\Deleted`, `\Draft`) and keywords in writable folders. Fetching message content from a writable folder sets `\Seen` unless the client uses `BODY.PEEK`. Read-only credentials, `EXAMINE`, and scope folders never set `\Seen`. `STORE` without `.SILENT` returns the updated flags.

Flags set on a received message in `INBOX` also apply to the same message in the credential's scope folders. Flags on copies in other folders, such as a custom folder, are independent.

<Note>
  IMAP flags and the [mailbox HTTP API](/mailboxes/http-api) share the same state. They are separate from the dashboard's read state: marking a message read in a mailbox does not mark it read in the dashboard, and the reverse is also true.
</Note>

## Known limitations

### Cross-session updates and retained history

New messages, expunges and moves are pushed to other open sessions on the same folder as `EXISTS` and `EXPUNGE`. Flag changes arrive as `FETCH FLAGS`, including changes made through HTTP. The update journal is stored in Postgres rather than in a gateway process, so it survives restarts. Expunge history is retained for approximately seven days; a session behind the retained history is disconnected and must reconnect and resynchronize rather than silently miss removals.

### Received-message deletion and moves

<Warning>
  `EXPUNGE` and `MOVE` do not delete the underlying received email. Expunging or moving a received message out of `INBOX` or a scope folder removes it from `INBOX` and every scope folder of that credential, and it stays removed there. It remains available through the API and dashboard, and in other credentials. Copying or moving it back into `INBOX` restores it. Don't use IMAP deletion as permanent deletion.
</Warning>

Moving a received message into a custom folder or `Trash` does create a copy there that stays until you expunge it. Moving it into `Junk` marks it as junk instead (see [Junk](#junk)). Messages created with `APPEND`, such as sent copies and drafts, are stored separately and are permanently removed when their last copy is expunged.

### Sent mail

Immediate sending through SMTP or the HTTP API with a `read_write` mailbox password saves a message in that credential's `Sent` in the background. Clients may still save their own copy with `APPEND`: a matching `Message-ID` already in `Sent` is deduplicated, in either order. Account-key sends also save to enabled read/write mailboxes with an exact sending-identity match; domain scopes alone do not select a mailbox. SMTP-only credentials and scheduled sends do not populate a mailbox. Historical sent email records are not backfilled.

<Warning>
  SMTP accepts messages up to 3 MiB, but client `APPEND` accepts at most 1 MiB. Automatic sent copies count toward the account's appended-storage quota. A sent-copy failure does not undo an accepted delivery or cause it to be retried.
</Warning>

### Junk

The [junk filter](/mailboxes/junk-filter) decides whether a received message belongs in `INBOX` or in `Junk`; it is never in both. Each credential can have [its own spam level and sender lists](/mailboxes/junk-filter#per-mailbox-spam-settings). Moving a received message from `INBOX` or a scope folder into `Junk` marks it as junk, and moving it from `Junk` back to `INBOX` marks it as not junk. The decision applies to this credential only, in IMAP and the mailbox API; it doesn't change other credentials, the account verdict or webhooks. Copying a received message into `INBOX` or `Junk` has the same effect.

New mail appears in `INBOX` or `Junk` once the junk filter has made its verdict, normally within a few seconds of arrival (at most about two minutes if filtering is unavailable). If the verdict that applies to this credential changes later, for example when the account verdict changes in the email API or dashboard and the credential has no decision of its own, the message moves between `INBOX` and `Junk` with its flags, and open sessions receive `EXPUNGE` for the folder it left and `EXISTS` for the folder it entered.

Expunging a received message from `Junk` removes it from the credential's folders; it doesn't return to `INBOX` if it is later marked as not junk. Messages appended to `Junk` are stored like other appended messages.

### Filters

[Mailbox filters](/mailboxes/filters) run once, when a received message first enters the credential's mailbox, and can move it to another folder, flag it or mark it as junk. A message a filter moved out of `INBOX` is no longer in `INBOX` or the scope folders, like any other move. Changing filters later doesn't re-sort existing mail.

### Guard-filtered messages

Messages blocked by Guard are not synchronized, and their content cannot be fetched. If a message is blocked after it was already synchronized, it is removed from the credential's folders the next time the client lists or opens a folder. Email clients may still show content they cached earlier.

## Scope changes and revoked access

When a credential's scopes, permissions, sender settings, enabled state, or password change, its active IMAP sessions receive `* BYE Mailbox credentials or scopes changed` and must reconnect. On the next folder listing or selection, folders for removed scopes disappear, and received messages that no longer match any remaining scope are removed from all of the credential's folders. Appended messages are not affected.

Each login rechecks that the login email's domain is verified, that at least one scope domain is verified, and that an exact sender identity is still covered by a verified scope. It also checks that the credential's `protocols.imap` is enabled and that the client address is in its `allowedIps` (see [Access and Limits](/mailboxes/access-and-limits)). If not, authentication fails with the same `NO [AUTHENTICATIONFAILED]` as a wrong password. Open sessions are rechecked periodically, currently about every five minutes, so a session that no longer passes these checks can stay open until the next recheck.

<Note>
  A domain losing its verified status does not disconnect an established IMAP session. To end current access, disable the credential, change its scopes or permissions, rotate its password, or delete it.
</Note>

## Message and storage limits

| Limit | Value |
| --- | --- |
| Maximum `APPEND` size | 1 MiB (`1,048,576` bytes), advertised as `APPENDLIMIT` |
| Appended storage per account | 250 MiB |
| Appended messages per account | 5,000 |
| Appended storage per credential | The credential's `storageQuotaBytes`, if set |

An `APPEND` over 1 MiB is rejected with `NO [TOOBIG]`. The account storage and message-count limits are shared by all of the account's credentials and folders. A credential's own [storage quota](/mailboxes/access-and-limits#storage-quota) counts each message it stored once, however many folders hold it. Exceeding either limit returns `NO [OVERQUOTA]`. For SMTP limits, see [Send with SMTP](/mailboxes/connect-smtp#limits).

## Connection limits and timeouts

| Limit | Value |
| --- | --- |
| TLS | Implicit TLS on port `993`, TLS 1.2 or later |
| Simultaneous connections per client IP address | 20 |
| Inactivity timeout before login | 60 seconds |
| Inactivity timeout after login | About 30 minutes |
| Maximum `IDLE` duration | 30 minutes |
| Failed logins | 10 per login address and IP address, and 50 per IP address, in a 15-minute window |

Connections over the per-IP limit receive `* BYE Too many connections from this address`. Once a login is throttled, attempts return `NO [AUTHENTICATIONFAILED]` until the window ends, even with the correct password. Authentication requests are also rate-limited by the API, so avoid reconnect loops and retry with backoff.

## Troubleshooting

| Symptom | Likely cause | What to check |
| --- | --- | --- |
| Authentication fails | Wrong login, rotated password, disabled credential, SMTP-only credential, IMAP turned off in `protocols`, client address outside `allowedIps`, unverified domain, or login throttling | Confirm the login email, current password, credential type, enabled state, protocols, allowed IPs, and verified domains. Wait 15 minutes after repeated failures. |
| An expected message is missing | Recipient is outside the scopes, the message is Guard-blocked, a filter moved it, or the folder hasn't been refreshed | Check the recipient, scope domains, Guard status, and the credential's filters, then reselect the folder |
| A scope folder rejects changes | `Scopes/*` folders are always read-only | Change the message in `INBOX` or copy it to a writable folder |
| A deleted received message is still in the dashboard or account API | Mailbox deletion only removes it from the credential's folders | Manage its account-level state through the dashboard or account email API |
| No sent copy appears | The copy is still pending, the send had no matching mailbox identity, or persistence failed | Use a `read_write` mailbox credential or exact sending identity and check available storage |
| Another device shows stale flags | The connection is offline or waiting for its next command | Reconnect or issue `NOOP`; active IDLE sessions receive flag updates automatically |
| The connection closes after a credential edit | Credential changes end active sessions | Reconnect with the current password and permissions |
