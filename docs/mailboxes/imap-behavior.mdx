Inbound presents received email through a managed IMAP mailbox rather than operating as a conventional standalone mail store. Understanding how folders, scopes, and synchronization interact helps avoid surprises in email clients.

## Default folders

Each mailbox credential includes these canonical folders:

| Folder | IMAP special-use attribute | Behavior |
| --- | --- | --- |
| `INBOX` | None | Combined incoming mail from every configured scope |
| `Sent` | `\Sent` | Available for client-saved sent messages; not populated automatically |
| `Drafts` | `\Drafts` | Available for client-saved drafts |
| `Trash` | `\Trash` | Available for client-organized messages |
| `Junk` | `\Junk` | Available for client-organized messages |

The hierarchy separator is `/`. `INBOX` and the default special-use folders cannot be deleted. Custom folders can be created, renamed, and deleted with a `read_write` credential. Incoming messages appear only when their original raw message content is available for IMAP retrieval.

### Scope folders

Every configured scope also appears as an individual folder:

```text
INBOX
Sent
Drafts
Trash
Junk
Scopes/*@example.com
Scopes/support@another-example.com
```

`Scopes` is a non-selectable container. A domain scope appears as `Scopes/*@example.com`; an address scope appears as `Scopes/support@example.com`.

These folders are filtered views of the same incoming messages available in `INBOX`, not independent writable mailboxes. They always open read-only, even when the credential has `read_write` access. You cannot append, move, or copy messages into a scope folder, or change its flags directly.

A `read_write` credential can copy messages from a read-only scope folder into a writable destination. A `read` credential cannot modify any folder.

## Supported IMAP features

The server supports `IMAP4rev1` and common operations used by desktop and mobile email clients:

- Authentication with `LOGIN` or `AUTHENTICATE PLAIN` over TLS.
- Folder discovery and selection with `LIST`, `LSUB`, `NAMESPACE`, `SELECT`, `EXAMINE`, `STATUS`, and special-use folders.
- Message retrieval and search with `FETCH`, `UID FETCH`, `SEARCH`, and `UID SEARCH`.
- Writable-folder operations with `STORE`, `COPY`, `MOVE`, `EXPUNGE`, `APPEND`, and applicable `UID` variants when the credential has `read_write` access.
- Folder management with `CREATE`, `RENAME`, and `DELETE`, subject to folder protections and access mode.
- Live message notifications with `IDLE`, plus `UIDPLUS`, `SPECIAL-USE`, `MOVE`, `ENABLE`, `UTF8=ACCEPT`, and `APPENDLIMIT` capabilities.

`SUBSCRIBE` and `UNSUBSCRIBE` are accepted for client compatibility, but subscription preferences are not persisted. `LSUB` returns all available folders rather than a separately maintained subscription list.

Capabilities are advertised through the standard `CAPABILITY` response. The default append-size capability is `APPENDLIMIT=1048576`. Although `WITHIN` may also be advertised, relative-age searches such as `OLDER` are not consistently implemented and should not be relied on.

<Note>
  `CONDSTORE`, `QRESYNC`, `HIGHESTMODSEQ`, `QUOTA` commands, and `COMPRESS=DEFLATE` are not available. `SORT`, `THREAD`, mailbox ACL extensions, and OAuth-based IMAP authentication are also not advertised or supported. Use a normal IMAP client configured for password authentication rather than requiring these extensions.
</Note>

The absence of the `QUOTA` extension does not mean appended messages are unlimited. Server-side append limits still apply.

### Search limitations

Searches by UID, flags, message size, and internal date operate on IMAP mailbox data. Header, subject, body, and other content-based searches depend on received-message metadata and may not find drafts or sent copies created through `APPEND`.

Unsupported search terms or headers can be ignored rather than rejected, which can produce broader results than requested. Treat advanced or relative-age searches as best-effort, and filter results in your application when exact matching matters.

## New-message notifications

`IDLE` is supported for near-real-time notification of new messages. The server also performs a periodic fallback refresh approximately every 60 seconds for active notification listeners.

An individual `IDLE` command can remain open for up to 30 minutes before the server ends the connection. Email clients should terminate and reissue `IDLE` periodically, or reconnect automatically after the server closes an expired idle session.

## Flags and read state

Writable credentials can update standard IMAP flags such as `\Seen`, `\Answered`, `\Flagged`, `\Deleted`, and `\Draft` through writable folders. Reading message content from a writable selected folder can automatically set `\Seen`; read-only credentials and read-only scope folders do not mark messages as seen.

For a given credential, flag changes on a received message are reflected across that credential's `INBOX` and corresponding scope views. Different credentials maintain their own IMAP flag state.

<Note>
  IMAP read and unread flags are independent of the dashboard's read state. Marking a message read in an IMAP client does not mark it read in the dashboard, and dashboard actions do not update the IMAP `\Seen` flag.
</Note>

## Scope changes and revoked access

When scopes or other credential permissions change, active IMAP sessions for that credential are logged out and must reconnect. On the next mailbox reconciliation, folders for removed scopes disappear, and received-message mappings that no longer match the remaining scopes are removed from the credential's folders.

This reconciliation applies to received messages throughout the credential's IMAP folders, not only `INBOX`. Messages created through IMAP `APPEND` are separate from received-message scope filtering.

New login attempts recheck both the login address's own verified domain and which scoped domain records remain verified. If the login domain is no longer verified, no verified scope remains, or an exact sender identity is no longer covered by a verified scope, authentication fails.

<Note>
  Changing a domain's verification status does not automatically disconnect an already-established IMAP session. To end current access, disable the credential, change its scopes or permissions, rotate its password, or delete it.
</Note>

## Message and storage limits

| Limit | Default |
| --- | --- |
| Maximum single IMAP `APPEND` | 1 MiB (`1,048,576` bytes) |
| Maximum SMTP message | 25 MiB (`26,214,400` bytes) |
| Total IMAP-appended storage per account | 250 MiB |
| Total IMAP-appended messages per account | 5,000 |
| Maximum SMTP recipients per message | 50 distinct envelope recipients |

The 250 MiB and 5,000-message limits are shared across the account's appended IMAP messages, not allocated separately to each folder or credential. Exceeding an append-storage limit results in an IMAP `OVERQUOTA` response.

The SMTP recipient limit applies to the combined distinct SMTP envelope recipients for a message, including recipients delivered as To, Cc, or Bcc.

### Sent mail is not saved automatically

Sending through SMTP does not automatically create a message in the IMAP `Sent` folder. Many email clients can save their own sent copy by issuing IMAP `APPEND` to `Sent`, which requires a `read_write` mailbox credential.

<Warning>
  SMTP accepts messages up to 25 MiB, but IMAP `APPEND` defaults to 1 MiB. A larger email can send successfully while the client's attempt to save its sent copy fails. Appended sent copies also consume the account-wide IMAP append quota. SMTP-only credentials cannot save an IMAP sent copy.
</Warning>

### Received-message deletion and moves

<Warning>
  IMAP deletion, `EXPUNGE`, and `MOVE` do not delete the underlying received email. Because `INBOX` and scope folders are rebuilt from the received-message source, a received message removed or moved out of `INBOX` can reappear during a later synchronization. Do not rely on IMAP deletion or moves as permanent deletion or durable removal from the incoming view.
</Warning>

This limitation concerns received messages synchronized from Inbound. Messages created only through `APPEND` are stored separately and are not re-created from the incoming-mail source after they are removed.

## Guard-filtered messages

Messages already marked as blocked by Guard are excluded from new IMAP synchronization, and fetching their raw message content is denied. If a previously visible message is later blocked, its existing server-side folder metadata can remain until the mailbox is listed or reopened and reconciliation runs.

<Note>
  Reopen or refresh the mailbox to reconcile newly blocked messages. An email client can also retain metadata or content it previously cached, so disappearance from every client view is not necessarily instantaneous.
</Note>

## Connection and authentication limits

IMAP permits up to 20 simultaneous connections from the same IP address by default. Repeated failed IMAP or SMTP logins are throttled after 10 failures for the same login and IP address within a 15-minute window; additional IP-wide failure protections also apply.

Separate authentication-request limits apply to successful and unsuccessful attempts alike: 60 attempts per minute for the same source IP and login address, and 3,000 attempts per minute per source IP. Avoid reconnect loops and retry with backoff.

SMTP submission also remains subject to account sending limits and the shared API rate limit. Temporary SMTP rate-limit or upstream failures can return `451`; clients should retry with backoff. See [API rate limits](/api-reference/rate-limits).

## Troubleshooting

| Symptom | Likely cause | What to check |
| --- | --- | --- |
| Authentication fails | Wrong login, rotated password, disabled credential, SMTP-only credential used for IMAP, or unverified scope | Confirm the exact login address, current generated password, credential type, enabled state, and verified domains |
| An expected message is missing | Recipient is outside the exact scopes, the message is Guard-blocked, its raw content is unavailable, or the client has not refreshed | Check the recipient, verified scope domains, Guard status, raw-message availability, and folder refresh |
| A scope folder rejects changes | `Scopes/*` folders are always read-only | Modify the message in `INBOX` or copy it to a writable folder |
| A received message returns after deletion or moving | Incoming folders synchronize from the underlying received-message source | Do not use IMAP deletion or moving as permanent deletion of received email |
| Sending succeeds but no sent copy appears | SMTP does not populate `Sent`, or the client's `APPEND` exceeded 1 MiB or the append quota | Enable client-side sent-copy saving, use a `read_write` mailbox, and check append size and storage limits |
| The connection closes after a credential edit | Credential or scope changes invalidate active IMAP sessions | Reconnect using the latest permissions and password |
| Repeated login attempts stop working | Authentication failure throttling is active | Correct the credentials and allow the rate-limit window to clear |
